## 1. 总体设计

一句话：**一个标准 RN 工程作根目录，内嵌一个完整、可独立构建的鸿蒙工程（`harmony/`）；两套包管理器各管一界（pnpm 管 JS、ohpm 管 ArkTS/原生）；构建期把三份运行时（JS / ArkTS / C++）粘合成一个 HAP。**

```
src/（DSH Connector）                   ← RN 项目根（Metro / JS 的世界，pnpm 管理）
├── index.js                           ← JS 入口：AppRegistry.registerComponent（≈ main.ts）
├── App.tsx                            ← 根组件（≈ App.vue）
├── app.json                           ← RN 应用元信息（名字）
├── package.json / pnpm-lock.yaml      ← JS 依赖（npm 生态）
├── metro.config.js                    ← Metro 打包配置（≈ vite.config.ts）
├── babel.config.js                    ← 转译层配置（RN 里显式存在）
├── tsconfig.json / jest.config.js / __tests__/   ← TS / 测试配套
│   （android/ ios/ 模板壳已于 2026-11-16 删除——本项目只用 HarmonyOS，需要时可由 RN CLI 重新生成）
│
└── harmony/                           ← 完整的 DevEco/OpenHarmony 工程（ohpm 管理）
    ├── AppScope/
    │   ├── app.json5                  ← 应用级配置：包名 com.yuban32.dshconnector、图标
    │   └── resources/                 ← 应用级资源（图标/媒体）
    ├── build-profile.json5            ← 工程级构建配置：product、签名、debug/release
    ├── build-profile.template.json5   ← 模板备份
    ├── codelinter.json                ← 代码检查配置
    ├── hvigor/ + hvigorfile.ts        ← hvigor 构建系统配置（≈ 整个构建脚本层）
    ├── oh-package.json5 (+lock)       ← 工程级 ohpm 依赖
    │
    └── entry/                         ← HAP 模块（装进模拟器/真机的本体）
        ├── build-profile.json5       ← 模块级构建：externalNativeOptions（abiFilters 在这）
        ├── oh-package.json5          ← 模块级 ohpm 依赖（RNOH 的 .har 挂在这）
        ├── hvigorfile.ts
        └── src/
            ├── main/
            │   ├── module.json5      ← Ability/页面声明（EntryAbility 注册处）
            │   ├── ets/              ← 【ArkTS 层】
            │   │   ├── entryability/   EntryAbility（应用入口，继承 RNOH 基类）
            │   │   ├── pages/          页面（挂 RNOH 的 RNApp）
            │   │   ├── PackageProvider.ets + RNOHPackagesFactory.ets ← ArkTS 侧包注册
            │   │   ├── codegen/        RN codegen 生成的 ArkTS 绑定（禁手改）
            │   │   └── workers/
            │   ├── cpp/              ← 【C++ 原生层】
            │   │   ├── CMakeLists.txt ← 编排 RNOH C++ 源码 + 应用原生代码
            │   │   ├── PackageProvider.cpp + RNOHPackagesFactory.h ← C++ 侧包注册
            │   │   ├── autolinking.cmake ← 自动生成的三方库链接清单（禁手改）
            │   │   └── generated/      RN codegen 生成的 C++ 绑定（禁手改）
            │   └── resources/        ← 模块级资源（字符串/主题）
            └── ohosTest/             ← 测试模块
```

## 2. 逐层职责

### 2.1 JS 层（项目根）

完全按 RN 官方模板组织。这样 Metro、babel、jest、IDE 的 RN 插件都按惯例工作，零特殊配置。
`index.js → App.tsx` 的入口链对应 Vue 的 `main.ts → App.vue`。

### 2.2 鸿蒙壳工程（harmony/）

**可以独立用 DevEco Studio 打开、单独构建**的完整工程。严格遵循 OpenHarmony 工程规范：

- `AppScope`（应用级：包名/图标）→ `entry`（模块级/HAP）→ `src/main`（module.json5 声明能力与页面）
- 包名、签名、构建产物全部从这里定义和产出
- `hvigor` 是鸿蒙侧的构建系统（类比 Gradle），配置在 `hvigor-config.json5` + 各级 `hvigorfile.ts`

### 2.3 entry 模块：三份运行时的汇聚点

- **ArkTS 层（ets/）**：鸿蒙原生 UI 与应用生命周期。RNOH 提供基类，壳工程只写薄壳
- **C++ 层（cpp/）**：RN 核心（Hermes 引擎、Fabric 渲染器等）以 `.so` 形式编出，JS 在里面执行
- **module.json5**：声明 EntryAbility 与路由，类比"应用清单"

### 2.4 双侧注册对与 codegen

最精妙的设计——**同名成对的注册文件**：

| ArkTS 侧 | C++ 侧 | 职责 |
|---|---|---|
| `PackageProvider.ets` | `PackageProvider.cpp` | 分别向 RNOH 框架注册"本应用有哪些 RN 包" |

接入每个三方 RN 库时，两侧都要补注册（`autolinking` 会自动生成大部分内容）。

**codegen 产物**（`ets/codegen/` 与 `cpp/generated/`）是 RN codegen 从 JS 组件规格生成的跨语言桥代码——**生成的，禁止手改**。

### 2.5 autolinking

`cpp/autolinking.cmake` 由 RNOH CLI 自动生成：每装一个三方库，它自动把原生部分挂进 CMake 链接。同样禁止手改。

## 3. 双包管理器与 .har 桥接

| 管理器 | 目录 | 管 | 类比 |
|---|---|---|---|
| pnpm | `node_modules/` | JS 世界依赖 | monorepo 里的 npm |
| ohpm | `harmony/oh_modules/` | ArkTS/原生依赖 | monorepo 里的 cargo |

**界桥是 `.har` 包**：RNOH 本体就是 `node_modules/@react-native-oh/react-native-harmony/react_native_openharmony.har` 被 ohpm 装进 `oh_modules`。三方库移植包（`@react-native-oh-tpl/*`）同理——npm 装移植包，其自带 `.har` 再挂进 `entry/oh-package.json5`（流程见教程 §7）。

## 4. 构建流水线分工

`npx react-native run-harmony --no-packager` 一条命令背后：

```
[1/3] ohpm 依赖检查（Metro 必须关着，防文件竞争）
[2/3] hvigor 构建
        ├─ ArkTS 编译（ets/ → abc 字节码）
        ├─ CMake + ninja：cpp/ + RNOH 源码 → libRNOHApp.so 等（abiFilters 决定编哪些 ABI）
        ├─ JS bundle：debug 不打包（运行时从 Metro 拉）；release 才打入
        └─ HAP 打包 + 签名
[3/3] hdc 安装到模拟器/真机并启动
```

debug 模式下运行链路：应用启动 → `hdc rport` 让模拟器 localhost:8098 映射主机（端口固定 8098，原因见教程 §6.8）→ 从 Metro 拉 bundle → Hermes 执行 → 原生渲染。

## 5. 产物与缓存目录（可安全删除，会重建）

| 目录/文件 | 内容 | 何时删 |
|---|---|---|
| `harmony/entry/build/` | hvigor 产物（HAP 中间物） | 构建异常/换签名时 |
| `harmony/entry/.cxx/` | CMake/ninja 缓存与对象文件 | CMake 配置污染、ABI 缓存错乱时（删后重配约 +25s） |
| `harmony/oh_modules/` | ohpm 依赖 | EPERM 残留、依赖损坏时（删后需重跑 ohpm install） |
| `harmony/.hvigor/` `harmony/.idea/` | 构建守护进程数据 / IDE 索引 | 一般不动 |

## 7. 禁改清单

| 路径 | 原因 |
|---|---|
| `harmony/entry/src/main/{cpp,ets}/{codegen,generated}/` | codegen 自动生成 |
| `harmony/entry/src/main/cpp/autolinking.cmake` | autolinking 自动生成 |
| `harmony/oh_modules/**` | 包管理器领地 |
| 各级 `.lock` 文件 | 需要变更时走包管理器命令 |
