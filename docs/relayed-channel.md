# 中继信道草案（relayed channel，未实现）

当中继方案落地时，它必须实现与直连信道相同的 RPC 信封与方法面（见 direct-channel-v1.md），仅替换底层可达性。本文记录当前接口约定与待定设计点，**当前 `RelayedChannel.serve()` 直接抛出未实现错误**。

## 接口约定

`ChannelAdapter`（src/channel/types.ts）是唯一约定：

- `serve(handler)`：把可达性抽象成 `(req: {identity, path, body}) => {status, body}` 的请求处理
- `advertise()`：产出邀约 URI 所需的端点列表（直连为主机地址；中继为 relay 端点 + 路由标识）
- `status`：`stopped / starting / ready / busy / error`，端口冲突等一律降级为状态而非异常

## 待定设计点（实现前必须决策）

1. **中继拓扑**：自建 relay 服务 or 复用现有基础设施；桌面与手机谁主动连 relay（建议：双向出站连接，桌面与手机各自连 relay，relay 按路由 id 配对转发）。
2. **路由标识与邀约**：`dsconnect://` URI 需扩展中继参数（如 `r=<routeId>`）；PSK 派生的 salt/info 需覆盖路由标识以防跨路由重放。
3. **帧与背压**：长连接建议改为帧协议（长度前缀 + 信封复用），并约定单帧上限与关闭帧；直连信道的短请求模型不适用。
4. **配额与滥用**：未认证连接的握手代价、每路由速率上限、邀约码爆破限速（当前直连由局域网可达性天然限速，中继没有这层保护）。
5. **密钥轮换**：入网完成后的会话密钥与设备 token 的轮换触发条件（token 泄露、长期未用、设备休眠唤醒）。

## 明确不做

- 中继侧不做任何明文感知——relay 只见密文，不参与信任建立；所有端到端认证仍由 PSK 派生 + 入网流程承担。
- 不在 v1 引入任何长连接依赖（`ws` 等留待实现时按需评估）。
